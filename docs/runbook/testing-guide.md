# HORUS — how to test every module, step by step

From launching Docker to reading the data in pgAdmin. Every command below was run on Windows 11 in
PowerShell against the code in this repository, on **synthetic data only**. Outputs shown as
"expected" are what those runs printed; ids, timestamps and durations will differ.

> **Data rule (CLAUDE.md §3).** The real World-Check feed never enters this repository and nobody
> (human or agent) pastes its names into a test. This guide uses an *invented* feed generated by
> `scripts/New-SyntheticFeed.ps1`. Step 6 of the plan — loading the real feed — is yours to run;
> see §16.

## 0. Conventions

- Shell: **Windows PowerShell**, working directory = the repository root
  (`...\HORUS-Draft`). Git Bash works for Gradle but **not** for `bootRun --args="…"` when an
  argument contains a space (this repository's path has spaces); that is why §6 onward uses
  `scripts\Invoke-Horus.ps1`, which sidesteps the problem.
- **Do not add `2>&1` to `docker` commands in PowerShell 5.1**: Docker prints progress on stderr and
  PowerShell shows it as a red error. It is not one. Check `$LASTEXITCODE` instead.
- "Expected:" blocks are approximate. Where an exact value matters it is stated.

## 1. Prerequisites

| Need | Check | Expected |
|---|---|---|
| Docker Desktop **running** | `docker info` | prints server info, no "cannot connect" |
| Java 21+ on PATH | `java -version` | `21` or newer (Gradle's toolchain compiles with 21) |
| Free ports | `Get-NetTCPConnection -LocalPort 5432,5050 -ErrorAction SilentlyContinue` | no output |
| Disk | — | ~3 GB for images and volumes |

Start Docker Desktop from the Start menu and wait for the whale icon to stop animating before
continuing. Everything that touches a database (the integration tests, the CLI) needs it.

## 2. One-time environment

```powershell
. .\scripts\Set-LocalEnv.ps1        # note the leading dot: it must run in YOUR session
```

Expected: `HORUS local environment set for this session:` with your operator name, the synthetic-feed
folder and the pgAdmin login. **Run it in every new PowerShell window** (it is fast).

What it does: creates random passwords once in `%USERPROFILE%\.horus-local\env.json` (outside the
repository, never committed), and sets `HORUS_DB_ADMIN_PASSWORD`, `HORUS_INGEST_PASSWORD`,
`HORUS_SCREEN_PASSWORD`, `HORUS_AUDIT_PASSWORD`, `HORUS_OPERATOR`, `PGADMIN_DEFAULT_*`.

> The database bakes these passwords into its four roles **the first time its volume is created**.
> If you ever delete `env.json`, also run `docker compose down -v` (§14) or the passwords will no
> longer match.

## 3. Start Docker and the database

```powershell
docker compose up -d db
docker compose ps
```

Expected: service `db`, status `Up … (healthy)`, ports `127.0.0.1:5432->5432/tcp`. (Bound to
loopback on purpose — the database is not reachable from the network.)

Verify what the init script created:

```powershell
docker compose exec -T db psql -U horus_admin -d horus -At -c "SELECT rolname FROM pg_roles WHERE rolname LIKE 'horus_%' ORDER BY 1"
docker compose exec -T db psql -U horus_admin -d horus -At -c "SELECT extname FROM pg_extension WHERE extname IN ('pg_trgm','unaccent') ORDER BY 1"
```

Expected: `horus_admin horus_audit horus_ingest horus_screen`, then `pg_trgm unaccent`.

There are **no tables yet**: the application creates its own schema (Flyway migrations V1–V7) the first
time it starts, using the admin credential. `docker compose exec -T db psql -U horus_admin -d horus -c "\dt"`
→ `Did not find any relations.`

## 4. Run the automated tests

```powershell
.\gradlew.bat build
```

Needs Docker running (the integration tests start throwaway PostgreSQL containers — they never use
your local `horus` database). First run takes several minutes.

Expected: `BUILD SUCCESSFUL`. This runs, in order: compile, every module's tests, the ArchUnit
dependency rules, and the ≥ 80 % line-coverage gate on `core`.

Run one module at a time when you are chasing a failure:

```powershell
.\gradlew.bat :domain:test                 # pure model: constructors reject invalid objects
.\gradlew.bat :core:test                   # normalisation, blocking, matching, ingestion SPI
.\gradlew.bat :application:test            # use cases against fakes: fail-closed, dominance, provenance
.\gradlew.bat :adapters:test               # real PostgreSQL: schema, roles, atomicity, blocking, e2e screening
.\gradlew.bat :bootstrap:test              # boots the WHOLE app against PostgreSQL; checks each role's datasource
.\gradlew.bat :architecture-tests:test     # the six dependency rules
.\gradlew.bat :core:test --tests "*WorkedExamplesTest"     # one class (spec §30 examples)
```

Read the results: `<module>\build\reports\tests\test\index.html` (open in a browser), or
`<module>\build\test-results\test\*.xml`. Coverage: `core\build\reports\jacoco\test\html\index.html`.

Which test guards which invariant: Appendix B.

> **OneDrive (fixed locally on 2026-09-25 — read this before your first build).** This checkout sits
> inside a OneDrive-synced folder, and OneDrive dehydrates Gradle's own output into cloud
> placeholders. Gradle then fails with `Unable to delete directory …\build\…`, or worse with
> `Cannot snapshot …\BenchmarkCommand.class: not a regular file` — and that second one does not
> clear by retrying.
>
> The fix in place is a **local, uncommitted** Gradle init script that moves every project's build
> directory out of the synced tree:
>
> ```
> C:\Users\<you>\.gradle\init.d\horus-local-build-dir.gradle
> ```
>
> With it, build output, test reports and JaCoCo reports live under **`C:\horus-build\<module>\`**
> instead of `<module>\build\`. Every report path in this guide should be read that way.
> `scripts\Invoke-Horus.ps1` looks in both locations and takes the newer jar, so it works with or
> without the script. Delete the file to go back to the default, and pause OneDrive sync instead.

## 5. Create the synthetic feed

The World-Check adapter refuses a load whose measured population statistics fall outside its
expectation (name/type/country 100 %, date of birth 27 % ±5, passport 0.74 % ±0.5). A hand-made
20-record file cannot pass that gate, so the generator produces **100 invented records with exactly
27 dates of birth and 1 passport**:

```powershell
. .\scripts\Set-LocalEnv.ps1 -Quiet
.\scripts\New-SyntheticFeed.ps1 -OutFile "$env:HORUS_SYNTHETIC_DIR\feed-v1.xml"
.\scripts\New-SyntheticFeed.ps1 -OutFile "$env:HORUS_SYNTHETIC_DIR\feed-v2.xml" -OmitUid wc-demo-3
```

Expected: `wrote 100 records to …\feed-v1.xml` and `wrote 99 records to …\feed-v2.xml`.
`feed-v2` is `feed-v1` minus one entity, to demonstrate a tombstone. The script **refuses to write
inside the repository** (a feed file must never be committable) — try it to see the guard.

Four fixed demo entities are always present; the rest are generated:

| uid | Name (invented) | Type | Note |
|---|---|---|---|
| `wc-demo-1` | Zorvan Talmesk | individual | DOB 1980-05-17, country EG, the only passport |
| `wc-demo-2` | Sahara Nile Trading Company | organisation | country SD |
| `wc-demo-3` | Quillon Marbrek | individual | DOB 1972, country KE — the one removed in `feed-v2` |
| `wc-demo-4` | Ostrel Vandermere | individual | country NG |

## 6. Load the watchlist (ingest)

`scripts\Invoke-Horus.ps1` runs one CLI command and returns its own exit code. It builds the jar on
first use (about a minute).

```powershell
$env:HORUS_FEED_PATH = "$env:HORUS_SYNTHETIC_DIR\feed-v1.xml"
.\scripts\Invoke-Horus.ps1 ingest --source=worldcheck
```

Expected (first load; also creates the schema):

```
outcome: PROMOTED
listVersionId: <uuid>
added=100 amended=0 unchanged=0 delisted=0 rejected=0
exit=0
```

**6a. Idempotent reload** — same file again:

```powershell
.\scripts\Invoke-Horus.ps1 ingest --source=worldcheck
```

Expected: `outcome: ALREADY_LOADED`, `added=0 … unchanged=0`, `exit=0`. No rows are written (checksum
short-circuit).

**6b. A removed entity becomes a tombstone (I-6):**

```powershell
$env:HORUS_FEED_PATH = "$env:HORUS_SYNTHETIC_DIR\feed-v2.xml"
.\scripts\Invoke-Horus.ps1 ingest --source=worldcheck
```

Expected: `outcome: PROMOTED`, **`added=0 amended=0 unchanged=99 delisted=1`**. The removed entity is
not deleted — it gets a `DELISTED` version and its earlier versions stay queryable (see §10).

**6c. The entity reappears** — load `feed-v1` again:

```powershell
$env:HORUS_FEED_PATH = "$env:HORUS_SYNTHETIC_DIR\feed-v1.xml"
.\scripts\Invoke-Horus.ps1 ingest --source=worldcheck
```

Expected: `amended=1 … unchanged=99` — a new ACTIVE version on the *existing* identity.

Then put the database back to a delisted state for §7 (so you can screen a de-listed entity):

```powershell
$env:HORUS_FEED_PATH = "$env:HORUS_SYNTHETIC_DIR\feed-v2.xml"
.\scripts\Invoke-Horus.ps1 ingest --source=worldcheck          # delisted=1 again
```

Other ingest commands (`confirm`, `rollback`) and reading the reconciliation report:
`docs/runbook/ingestion.md`.

## 7. Publish a config and screen names

### 7a. Screening is unavailable until a configuration exists

```powershell
.\scripts\Invoke-Horus.ps1 screen --name "Zorvan Talmesc" --type INDIVIDUAL
```

Expected: `ERROR: screening unavailable: no approved configuration for profile default`, **exit 3**. The
system refuses to guess; an unavailable screening is never a clear (I-1).

### 7b. Publish the configuration

```powershell
.\scripts\Invoke-Horus.ps1 publish-config --defaults --approved-by compliance-lead
```

Expected: `configVersionId: <uuid>`, `alertThreshold: 55`, `strongMatchThreshold: 75`, `exit=0`.

> The defaults are the spec §16.2 starting point with **placeholder** thresholds. Publishing them is
> mechanical; it is **not** an approved operating point (spec §16.4 — that is Compliance's call, made
> on benchmark evidence). To publish your own values use `--file`, e.g.
> `--file scripts\samples\config-valid.json`.

The configuration is validated when published: an invalid one is refused and nothing is saved (§13).

### 7c. Screen

```powershell
.\scripts\Invoke-Horus.ps1 screen --name "Zorvan Talmesc" --type INDIVIDUAL --dob 1980 --country EG --idempotency-key demo-1
```

Expected (ids differ; the score should be similar):

```
screeningId: <uuid>
outcome: STRONG_MATCH
listVersionIds: [<uuid>]
configVersionId: <uuid>
pipelineVersion: 1.0.0
subject 1: STRONG_MATCH, candidates=2, topScore=94
  #1 score=94 STRONG_MATCH entity=<uuid> matched="Zorvan Talmesk"
  #2 score=49 NO_MATCH entity=<uuid> matched="Talthar Zorvan"
exit=2
```

- **Exit code is meaningful**: `0` NO_MATCH · `1` POSSIBLE_MATCH · `2` STRONG_MATCH · `3` ERROR/unavailable ·
  `64` bad input. Scripts must treat `3` as a halt, never as a clear.
- The result carries its provenance (I-12): `listVersionIds`, `configVersionId`, `pipelineVersion`.
- The **screened name is never printed back** and never logged (I-11). The *listed* entity's name is.
- Every candidate the engine scored is kept — even `#2` at 49 — because nothing may be dropped (I-8).

Read it back exactly as stored (nothing is recomputed — I-3). Use the `screeningId` from above:

```powershell
.\scripts\Invoke-Horus.ps1 show-screening --id <screeningId> --explain
```

Each candidate's JSON lists the five feature scores with their weights, every attribute effect with
its reason, the thresholds used and the band. You can recompute the score by hand:
`composite = round(clamp(0,100, 100 × Σ wᵢsᵢ / Σ wᵢ + Σ effects))`.

**Idempotency:** repeat the exact `screen` command with `--idempotency-key demo-1`. Expected:
`outcome: STRONG_MATCH (replayed)` and the *same* `screeningId` — nothing is re-scored or re-stored.

### 7d. A de-listed entity is still found — demoted, with a reason (I-8)

```powershell
.\scripts\Invoke-Horus.ps1 screen --name "Quillon Marbrek" --type INDIVIDUAL --idempotency-key demo-2
```

Expected: `#1 score=90 STRONG_MATCH … matched="Quillon Marbrek"` — an exact name (100) minus the −10
de-listed demotion. It is **not** removed. Confirm the reason in the stored explanation:

```powershell
.\scripts\Invoke-Horus.ps1 show-screening --id <screeningId-from-above> --explain
```

Look for `"attribute":"status","delta":-10.0,"reason":"de-listed in the latest list version but may
still be designated elsewhere; demoted, not removed"`.

### 7e. Other things to try

```powershell
.\scripts\Invoke-Horus.ps1 screen --name "Wexler Pomfrett" --type INDIVIDUAL          # a clear name: exit 0, still recorded
.\scripts\Invoke-Horus.ps1 screen --name "Sahara Nile Trading Co" --type ORGANISATION # an organisation variant
.\scripts\Invoke-Horus.ps1 screen --name "Trading" --type ORGANISATION                # a bare generic word: must not match broadly
.\scripts\Invoke-Horus.ps1 screen --name "Zorvan Talmask" --identifier ZT1234567     # an identifier match forces at least the strong threshold
.\scripts\Invoke-Horus.ps1 screen --names-file .\scripts\samples\names.txt            # several subjects in one request (ERROR dominates)
.\scripts\Invoke-Horus.ps1 screen --name "x" --dob 19x0                               # bad input: exit 64
```

> **Known gap:** an identifier only affects candidates that *name* blocking has already surfaced. The
> spec (§15.1) also lists an identifier lookup as a way to *find* candidates; that path is not built,
> so a query with a correct passport number but an unrecognisable name is not retrieved. See D12.

## 8. Measure blocking recall

Recall lost at stage 1 is invisible to stage 2, so it is measured on its own (CLAUDE.md §10). The
sample corpus (`scripts\samples\blocking-corpus.tsv`, tab-separated `query<TAB>sourceEntityId`) refers to
the four demo entities:

```powershell
.\scripts\Invoke-Horus.ps1 measure-blocking --source worldcheck --corpus .\scripts\samples\blocking-corpus.tsv
```

Expected:

```
cases: 5
recall[EXACT_HASH]: 0.6000 (3/5)
recall[TRIGRAM]: 1.0000 (5/5)
recall[PHONETIC]: 1.0000 (5/5)
recall[combined]: 1.0000 (5/5)
meanCandidateSetSize: 1.80
partialCases: 0
truncatedCases: 0
missedCaseIndexes (0-based, corpus order): []
```

Exact-hash alone misses spelling variants; the **union** of strategies recovers them (I-2). A
malformed line or an unknown expected entity makes the run **fail** rather than shrink the
denominator — try adding a line with only one column, or an unknown id: exit 2 / 64 with the line number.

## 9. Run the benchmark

The benchmark pushes a labelled corpus through the *same* screening use case a consumer would call,
then reports recall first, then precision, alert volume, every missed true positive, and a threshold
sweep.

```powershell
.\scripts\Invoke-Horus.ps1 benchmark --source worldcheck --corpus .\scripts\samples\benchmark-corpus.tsv --out-dir "$env:HORUS_SYNTHETIC_DIR\bench-out" --sweep 40,50,55,60,70,80,90
```

Expected (the sample includes one deliberately wrong label, so one miss is *supposed* to appear):

```
recall: 0.8571 (6 of 7 true positives) at threshold 55
precision: 1.0000  f1: 0.9231  fp-per-1000-clear: 0.00
cases: 10 (positives 7, clear 3)
missedTruePositives: 1
errorCases: 0
exit=1
```

Exit `1` = at least one miss, `3` = at least one ERROR, `0` = neither. Open the outputs:

```powershell
Get-Content "$env:HORUS_SYNTHETIC_DIR\bench-out\benchmark-summary.md"   # recall first; misses by line; the sweep; limits
Import-Csv  "$env:HORUS_SYNTHETIC_DIR\bench-out\benchmark-sweep.csv"  | Format-Table    # precision/recall by threshold
Import-Csv  "$env:HORUS_SYNTHETIC_DIR\bench-out\benchmark-cases.csv"  | Format-Table    # per-case outcome by corpus line
```

- Misses are listed by **corpus line number**, never by name (I-11), with a reason:
  `NOT_A_CANDIDATE` (a stage-1 loss) or `SCORED_BELOW_THRESHOLD` (a stage-2 loss).
- The summary states that **no recommendation to rely on HORUS may be made while an unexplained miss
  remains**, and that a small corpus gives wide error bars (the spec wants 1,000 cases).
- The corpus format and the meaning of each column: the header comment in
  `scripts\samples\benchmark-corpus.tsv`. For the **real** run set `HORUS_BENCHMARK_PATH` (or `--corpus`)
  to the corpus you build with Compliance — see §16.

## 10. See the data in pgAdmin

### Option A — pgAdmin in Docker (recommended; nothing to install)

```powershell
. .\scripts\Set-LocalEnv.ps1
docker compose --profile tools up -d pgadmin
```

Open **http://localhost:5050** and log in with the email `horus@example.com` and the password from
`%USERPROFILE%\.horus-local\env.json` (`PGADMIN_DEFAULT_PASSWORD`). To print it: 
`(Get-Content $HOME\.horus-local\env.json | ConvertFrom-Json).PGADMIN_DEFAULT_PASSWORD`.

Under **Servers → HORUS local** four connections are pre-registered, one per database role.
Right-click one → *Connect Server* → enter that role's password (from the same `env.json`:
`HORUS_SCREEN_PASSWORD`, `HORUS_AUDIT_PASSWORD`, `HORUS_INGEST_PASSWORD`, `HORUS_DB_ADMIN_PASSWORD`).

| Connection | Use it to | You will notice |
|---|---|---|
| **admin** | see everything; draw the ERD | owns the schema |
| **screen** | read the watchlist and screenings | cannot read `audit_event` |
| **audit** | read the audit trail | can read nothing else; an `UPDATE` is refused |
| **ingest** | see what the loader can write | cannot read `screening_*` |

Then: **Databases → horus → Schemas → public → Tables**. Right-click a table → *View/Edit Data →
All Rows*. Open **Tools → Query Tool** (on the `horus` database) to run the queries below.

### Option B — pgAdmin installed on Windows

Register a server: **Host** `localhost`, **Port** `5432`, **Maintenance database** `horus`,
**Username** one of the four roles above, **Password** from `env.json`. (The Docker container binds
to loopback only, so `localhost` works and other machines cannot connect.)

### Option C — psql (no GUI)

```powershell
docker compose exec -T db psql -U horus_admin -d horus -c "SELECT status, count(*) FROM list_version GROUP BY 1"
```

### Entity-relationship diagram

In pgAdmin: right-click the database **horus → ERD For Database**. You get every table and foreign
key: `list_version` → `watch_entity_version` → the children keyed on `entity_version_id`
(`watch_name`, `watch_dob`, …), and `screening_request` → `screening_subject` → `screening_candidate`.

### Queries worth running

Paste into the Query Tool (as **admin** or **screen**, except where noted).

```sql
-- 1. Every load, and which one is live. One ACTIVE; older ones SUPERSEDED; failed ones FAILED.
SELECT list_version_id, source_id, status, record_count, loaded_at, pipeline_version
FROM list_version ORDER BY loaded_at;

-- 2. What the loader measured about the source (drives which comparators may be enabled).
SELECT source_id, jsonb_pretty(capabilities) FROM list_version WHERE status = 'ACTIVE';

-- 3. The life of two entities: versions, and the load each came from. Note the DELISTED tombstone
--    for wc-demo-3 and that its earlier versions are still there (I-6: nothing is deleted).
SELECT we.source_entity_id, wev.status AS version_status, lv.status AS load_status, lv.loaded_at, wev.content_hash
FROM watch_entity we
JOIN watch_entity_version wev ON wev.entity_id = we.entity_id
JOIN list_version lv ON lv.list_version_id = wev.list_version_id
WHERE we.source_entity_id IN ('wc-demo-1', 'wc-demo-3')
ORDER BY we.source_entity_id, lv.loaded_at;

-- 4. "Current" entity state (unchanged entities keep the version from the load that last changed them).
SELECT status, count(*) FROM current_watch_entity_version GROUP BY status;

-- 5. The normalised forms every name was stored and indexed under (the SAME pipeline the query uses, I-10).
SELECT raw_name, normalised_name, name_tokens, phonetic_codes, script
FROM watch_name ORDER BY raw_name LIMIT 25;

-- 6. Screenings: outcome, provenance and the top score. (query_name is the screened name: evidence, restrict access.)
SELECT r.requested_at, r.outcome AS request_outcome, s.outcome AS subject_outcome, s.top_score,
       s.candidate_count, r.config_version_id, r.list_version_ids, r.pipeline_version
FROM screening_request r JOIN screening_subject s USING (screening_id)
ORDER BY r.requested_at DESC;

-- 7. One candidate's whole stored explanation, pretty-printed.
SELECT c.rank, c.composite_score, c.decision_band, jsonb_pretty(c.explanation_json::jsonb) AS explanation
FROM screening_candidate c ORDER BY c.composite_score DESC LIMIT 3;

-- 8. The score broken into its attribute effects (why a candidate was demoted or promoted).
SELECT c.rank, c.composite_score, e ->> 'attribute' AS attribute, e ->> 'delta' AS delta, e ->> 'reason' AS reason
FROM screening_candidate c, json_array_elements(c.explanation_json -> 'effects') e
ORDER BY c.composite_score DESC, attribute LIMIT 30;

-- 9. The configuration each screening ran on (I-7 / I-12).
SELECT config_version_id, profile_id, created_by, approved_by, effective_from,
       payload ->> 'alertThreshold' AS alert, payload ->> 'strongMatchThreshold' AS strong
FROM config_version ORDER BY created_at;

-- 10. The audit trail -- ids and counts, never names. Run as the AUDIT or ADMIN connection.
SELECT occurred_at, event_type, actor, subject_type, subject_id, payload
FROM audit_event ORDER BY occurred_at DESC LIMIT 50;

-- 11. Prove there is no name in the audit trail (should return 0).
SELECT count(*) FROM audit_event WHERE payload::text ILIKE '%zorvan%' OR payload::text ILIKE '%marbrek%';
```

## 11. Measure blocking latency at scale

Reproduces the numbers in `docs/adr/ADR-003-blocking-index-strategy.md`. It builds a **scratch**
database with 500,000 invented entities next to `horus` (never inside it) and times the exact SQL the
blocking adapter runs. Takes ~2 minutes to generate.

```powershell
. .\scripts\Set-LocalEnv.ps1 -Quiet
docker compose exec -T db psql -U horus_admin -d horus -c "CREATE DATABASE horus_scale"
docker compose exec -T db psql -U horus_admin -d horus_scale -c "CREATE EXTENSION pg_trgm" -c "CREATE EXTENSION fuzzystrmatch"
# Apply the project's migrations to the scratch database:
Get-ChildItem .\adapters\src\main\resources\db\migration\V*.sql | Sort-Object Name | ForEach-Object {
  Get-Content $_.FullName -Raw | docker compose exec -T db psql -q -v ON_ERROR_STOP=1 -U horus_admin -d horus_scale }
Get-Content .\scripts\scale-test\01-generate.sql -Raw    | docker compose exec -T db psql -q -v ON_ERROR_STOP=1 -U horus_admin -d horus_scale
Get-Content .\scripts\scale-test\02-time-blocking.sql -Raw | docker compose exec -T db psql -X -q -U horus_admin -d horus_scale
```

Read the `Execution Time:` lines. Expected order of magnitude: exact-hash and phonetic **sub-millisecond**;
trigram at threshold 0.3 **tens to hundreds of milliseconds**, falling steeply as the threshold rises
(the last block prints how many rows each threshold matches). Timings vary 2–3× between runs; read the
magnitude, not the digits. Clean up:

```powershell
docker compose exec -T db psql -U horus_admin -d horus -c "DROP DATABASE horus_scale"
```

## 12. Prove the security controls by hand

Segregation of duties is enforced by the **database**, not by code discipline. In pgAdmin's Query
Tool (or psql) connect **as the restricted role** and try to break it — every attempt below must be
refused (`permission denied`, SQLSTATE 42501). A test that connected as the owner would prove nothing.

```powershell
. .\scripts\Set-LocalEnv.ps1 -Quiet
# as horus_audit: append-only evidence (I-5)
docker compose exec -T -e PGPASSWORD=$env:HORUS_AUDIT_PASSWORD db psql -h db -U horus_audit -d horus -c "UPDATE audit_event SET actor = 'x'"
docker compose exec -T -e PGPASSWORD=$env:HORUS_AUDIT_PASSWORD db psql -h db -U horus_audit -d horus -c "DELETE FROM audit_event"
# as horus_screen: cannot alter stored screenings, cannot read the audit trail, cannot write the watchlist
docker compose exec -T -e PGPASSWORD=$env:HORUS_SCREEN_PASSWORD db psql -h db -U horus_screen -d horus -c "UPDATE screening_request SET outcome = 'NO_MATCH'"
docker compose exec -T -e PGPASSWORD=$env:HORUS_SCREEN_PASSWORD db psql -h db -U horus_screen -d horus -c "SELECT * FROM audit_event"
docker compose exec -T -e PGPASSWORD=$env:HORUS_SCREEN_PASSWORD db psql -h db -U horus_screen -d horus -c "DELETE FROM watch_name"
```

### 12a. Run the three CI security gates locally

CI runs SAST, a dependency scan and a secret scan, and a high-severity finding must fail the build

**Dependency scan (OWASP dependency-check).**

```powershell

```

Use **`dependencyCheckAggregate`**, never `dependencyCheckAnalyze`. This is a multi-project build and
the root project declares no dependencies of its own, so `Analyze` at the root scans **zero**
dependencies and still prints "Found 0 vulnerabilities" — a pass that means nothing. Always read
`Dependencies Scanned:` in the report; if it says `0`, the run told you nothing.

Report: `build/reports/dependency-check-report.html` (and `.json`). The build **fails on CVSS ≥ 7.0**.

Expected today: `Found 0 vulnerabilities`, **BUILD SUCCESSFUL**, with `Dependencies Scanned: 71`.

`config/dependency-check-suppressions.xml` — a false CPE match that maps JaCoCo's

## 13. Fail-closed drills

The rule (I-1): an unavailable or incomplete screening is an explicit **error**, never a clear.

| Drill | Command | Expected |
|---|---|---|
| Database down | `docker compose stop db`, then `.\scripts\Invoke-Horus.ps1 screen --name "Zorvan Talmesc"` | non-zero exit, **never** exit 0; then `docker compose start db` |
| Invalid config refused | `.\scripts\Invoke-Horus.ps1 publish-config --file .\scripts\samples\config-invalid-thresholds.json --approved-by lead` | `refused: invalid matching configuration: thresholds must satisfy 0 < alertThreshold < strongMatchThreshold <= 100 …`, exit 3, **nothing saved** |
| Valid config accepted | `.\scripts\Invoke-Horus.ps1 publish-config --file .\scripts\samples\config-valid.json --approved-by lead` | `configVersionId: …`, thresholds 60/80. The next `screen` uses it (`configVersionId` changes) |

| Ingest a bad file | point `HORUS_FEED_PATH` at a file of malformed XML | `REJECTED` with the reject reason, the previous version keeps serving |

After the database-down drill: `docker compose start db` and wait for `(healthy)`.

## 15. Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `docker: error during connect … dockerDesktopLinuxEngine` | Docker Desktop is not running. Start it, wait for the engine, retry. |
| `required variable HORUS_… is missing a value` (from `docker compose`) | You did not dot-source `. .\scripts\Set-LocalEnv.ps1` in this window. |
| `Configuration error: HORUS_… is not set` and **exit 78** | The credential for the role that command needs is absent. The message names the variable and the remedy. Dot-source `. .\scripts\Set-LocalEnv.ps1`, then re-run. A command only needs the roles it uses: `ingest` does **not** need `HORUS_SCREEN_PASSWORD`. |
| `Could not resolve placeholder 'HORUS_SCREEN_PASSWORD'` + ~200 stack frames | A build from before this was fixed. Rebuild (`.\gradlew.bat build`). Credentials are now resolved on first use, with a one-line message. |
| `password authentication failed for user "horus_…"` | The volume was created with different passwords. `docker compose down -v`, then start again (§14). |
| `port is already allocated` / `bind … 5432` | Another PostgreSQL uses 5432. Stop it, or change the left-hand port in `docker-compose.yml`. |
| Gradle: `Unable to delete directory …\build\…` or `Cannot snapshot ….class: not a regular file` | OneDrive has dehydrated the build output. The installed init script (§3) moves the build directory to `C:\horus-build`; if it is missing, reinstall it, or pause OneDrive sync, run `.\gradlew.bat --stop` and delete the `build` folders. They are generated output. |
| `'C:\Users\…\OneDrive' is not recognized` from `bootRun --args="…"` | Git Bash / spaces in the path. Use `scripts\Invoke-Horus.ps1`. |
| `Cannot subclass final class …` at startup | A persistence adapter was made `final` **and** annotated `@Repository`. Use `@Component` — see ADR-004. `ApplicationBootTest` guards this. |
| A screening says `no active list version` | Nothing has been ingested (or the load was REJECTED). Run §6. |
| A screening says `… re-ingest required` | The active list was normalised with a different pipeline version than the running code (I-10). Re-ingest. |
| `rejected` count in an ingest | See the reconciliation report; a load with > 5 % rejected records fails. `docs/runbook/ingestion.md`. |
| A capability-gate rejection on a hand-made feed | The World-Check gate expects realistic population statistics; use `New-SyntheticFeed.ps1` (100 records). |
| pgAdmin container exits at once | `PGADMIN_DEFAULT_PASSWORD` was empty: dot-source `Set-LocalEnv.ps1` first. |
| pgAdmin cannot connect to a server | Use the container's network name `db` (already set) — not `localhost` — inside pgAdmin-in-Docker. |

## 16. What only you can do (real data)

These are **not** delegable (CLAUDE.md §3, plan steps 6, 7 and 10):

### 16.0 Pre-flight before the first real load — do these in order

**A. Start from an empty database.** After following this guide your database holds *synthetic*
entities under `source_id = 'worldcheck'` — the same source id the real feed uses. Loading the real
feed on top of them means: the anomalous-delta gate trips (a 5.99M-vs-100 delta) so the load runs for
hours and then halts at `AWAITING_CONFIRMATION`; the synthetic entities are tombstoned as
"de-listed"; and real and invented names are interleaved in one source's version history — which
**cannot be cleaned up afterwards**, because versions are immutable (I-6).

```powershell
. .\scripts\Set-LocalEnv.ps1
docker compose --profile tools down -v      # deletes the volume, synthetic data included
docker compose up -d db                     # wait for (healthy); the schema is recreated on first run
docker compose exec -T db psql -U horus_admin -d horus -At -c "SELECT count(*) FROM list_version"
```

The last command must error (no such table) or return `0`. If it returns anything else, you are not
starting clean.

**B. Prove the mapping on a small extract first.** The reject-fraction check and the capability gate
only run *after* the whole file has streamed, so a mis-mapped field or a wrong element name costs the
entire run. Ten seconds now saves hours:

```powershell
.\scripts\New-FeedExtract.ps1 -SourceFile $env:HORUS_FEED_PATH -OutFile C:\horus-data\extract-200.xml -Records 200
```

It streams the file (never loads it), reports the **root and record element names**, and says whether
the record element matches the configured `XmlFormatReader("record")`. If it reports a mismatch, stop
and fix `bootstrap/src/main/java/horus/bootstrap/IngestionConfig.java` — otherwise ingestion finds
zero records. Then load the extract under a **throwaway source id** so the real source's history
stays clean, and check the counts and the capability report before the full run.

**C. Run it as a process that will not be interrupted.** Use `scripts\Invoke-Horus.ps1` (it runs
`java -jar`), not `gradlew bootRun` — a Gradle daemon timeout or an IDE restart will kill a `bootRun`
process mid-load. Expect it to be slow: the file is read twice (once to checksum), child rows are
inserted one at a time, and a structural pass alone took 229 s (D12 M-2, M-3).

**D. Capacity — checked on this machine, no action needed.** 31.5 GB RAM (default JVM max heap
≈ 7.9 GB, comfortably above the ~0.6–1 GB the in-memory `seen` set of 6M source ids needs on a first
load) and 695 GB free disk against an estimated few GB for tables and indexes. On a smaller machine,
set `-Xmx4g` and re-check disk.

**E. Confirm `HORUS_OPERATOR` identifies you** — it is recorded as the actor on every audit event for
this load. `Set-LocalEnv.ps1` defaults it to your Windows username.

**F. Know the failure behaviour before you start.** A rejected or interrupted load leaves the
previous version serving (no previous version, on a clean database, means nothing is served — which
is the fail-closed outcome, not a silent empty result). Nothing is ever partially committed
(`TransactionAtomicityIntegrationTest`).


1. **Load the real feed** (plan Step 6): set `HORUS_FEED_PATH` to the real file *outside* the
   repository, run `ingest --source=worldcheck`, and check `docs/runbook/ingestion.md` — counts
   reconcile to **5,990,394**, the checksum is recorded, and the measured capabilities match spec §6
   within tolerance. Expect this to take a long time (a structural pass alone was 229 s).
2. **Measure blocking recall on real data** (Step 7): build a labelled corpus of query names and their
   expected entities and run `measure-blocking`. **If combined recall is below Compliance's floor,
   stop — scoring cannot recover what blocking lost.**
3. **Build the benchmark corpus with Compliance** (Step 10): target 200 cases (the spec wants 1,000 —
   say so in D12), run `benchmark`, and review **every** missed true positive individually. Then choose
   a threshold with Compliance, and publish it with `publish-config --file … --approved-by <name>`.
4. **Time blocking and end-to-end screening on the real load** — the 500k-row synthetic run in §11 is
   only an order of magnitude (ADR-003 lists what to measure).

Never paste a real listed name into a fixture, a test, a comment or a commit message.

## Appendix A — CLI reference and exit codes

Run any of these as `.\scripts\Invoke-Horus.ps1 <command> [options]`.

| Command | Purpose | Key options |
|---|---|---|
| `ingest` | Load `HORUS_FEED_PATH` and reconcile | `--source=worldcheck` |
| `confirm` | Confirm/reject a load awaiting confirmation (delta > 20 %) | see `--help` |
| `rollback` | Repoint to the previously active list version | `--source`, `--reason` |
| `publish-config` | Validate and publish a new config version | `--defaults` or `--file`, `--approved-by`, `--profile` |
| `screen` | Screen one or more names | `--name` / `--names-file`, `--type`, `--dob`, `--country`, `--identifier`, `--profile`, `--idempotency-key` |
| `show-screening` | Show a stored screening | `--id`, `--explain` |
| `measure-blocking` | Blocking recall per strategy | `--source`, `--corpus` |
| `benchmark` | Recall/precision/sweep on a corpus | `--source`, `--corpus` (or `HORUS_BENCHMARK_PATH`), `--out-dir`, `--sweep` |

Exit codes — `screen`: **0** NO_MATCH · **1** POSSIBLE_MATCH · **2** STRONG_MATCH · **3** ERROR or
unavailable · **64** bad input · **78** configuration error (a required credential is not set; any
command can return this). `ingest`: **0** promoted / already loaded · **1** rejected · **2** feed
path missing · **3** awaiting confirmation. `benchmark`: **0** no misses/errors · **1** misses ·
**2** unresolved expected entity · **3** errors/unavailable · **64** bad input. `measure-blocking`: **0**
all found · **1** a miss or partial case · **2** unresolved expected entity.

Environment variables: `HORUS_DB_ADMIN_PASSWORD`, `HORUS_INGEST_PASSWORD`, `HORUS_SCREEN_PASSWORD`,
`HORUS_AUDIT_PASSWORD` (required); `HORUS_OPERATOR` (who is acting); `HORUS_FEED_PATH`;
`HORUS_BENCHMARK_PATH`; optional `HORUS_DB_HOST`, `HORUS_DB_PORT`, `HORUS_DB_NAME`;
blocking: `HORUS_BLOCKING_STRATEGIES` (default `EXACT_HASH,TRIGRAM,PHONETIC`),
`HORUS_BLOCKING_MAX_CANDIDATES` (500), `HORUS_BLOCKING_TRIGRAM_THRESHOLD` (0.3).
